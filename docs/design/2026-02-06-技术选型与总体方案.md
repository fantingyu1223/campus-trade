### 1.3 关键约束落地结论

- **微信支付资质是本项目最大外部风险**：个人主体小程序不能开通微信支付（详见 §6.1 核实结论与对策）。本方案的订单/支付模型按"支付通道可插拔"设计，不依赖微信支付即可跑通全部流程。
- 零预算：优先永久免费额度方案；唯一可能必需的现金支出为域名（约 ¥55/年）与轻量服务器（学生机约 ¥100/年，可用免费方案替代，见 §2.5）。
- 域名 ICP 备案约需 15-20 个工作日，须在 2 月中旬前启动，否则阻塞 3 月上线（小程序要求 HTTPS + 已备案域名）。

## 2. 技术栈选型及理由

选型原则：单人维护 > 社区成熟度 > 免费额度 > 性能。不追新、不引入微服务、不引入中间件全家桶。架构形态经 2026-02-06 评审定为模块化单体（方案 B，待用户拍板），对比分析见附录 A；部署形态不变（单容器），解耦通过模块纪律实现。

### 2.1 小程序端框架

| 项 | 结论 |
|---|---|
| **选型** | **微信原生小程序框架**（WXML/WXSS + TypeScript + npm 构建） |
| 备选 A | uni-app（Vue3 语法，可多端） |
| 备选 B | Taro（React 语法，可多端） |
| **理由** | ① 只交付微信小程序一端，跨端框架的抽象层是纯成本；② 原生框架无编译黑盒，调试订阅消息、登录、上传等微信能力最直接，文档与社区问题答案最全；③ 单人维护，减少一层依赖即减少一类故障；④ TypeScript 可在编译期对齐 §5 API 契约。若未来确需 App/H5 端，重写页面层成本可控（业务逻辑在服务端）。 |
| UI 库 | WeUI-miniprogram / 自写组件为主；不引入重型组件库（小程序包体积 ≤2MB 主包限制）。 |

### 2.2 后端运行时与框架

| 项 | 结论 |
|---|---|
| **选型** | **Node.js 20 LTS + NestJS（TypeScript）+ Prisma ORM** |
| 备选 A | Node.js + Express/Koa（更轻，但结构全靠自律，单人项目后期易腐化） |
| 备选 B | Java + Spring Boot（成熟但资源占用高、单人迭代慢、免费服务器 1-2GB 内存跑 JVM 紧张） |
| 备选 C | Python + FastAPI（与前端不同语言，无法共享契约类型；异步生态不如 Node 贴合 IO 密集场景） |
| **理由** | ① 与小程序端同为 TypeScript，DTO/枚举可复用，契约变更一处改两端编译报错，单人维护成本最低；② NestJS 模块化结构与 §3 模块划分一一对应，内置校验（class-validator）、拦截器、异常过滤器，正好承载统一错误码规范；③ Prisma 的 schema 即本文 §4 表结构的单一事实源，迁移可回溯；④ 业务为典型 CRUD+状态机 IO 密集型，Node 性能完全够用。 |

### 2.3 数据库

| 项 | 结论 |
|---|---|
| **选型** | **MySQL 8.0**（InnoDB，utf8mb4，REPEATABLE READ 默认隔离级） |
| 备选 A | PostgreSQL（功能更强，如 JSONB、全文检索；但国内云平台免费/低价实例与运维资料以 MySQL 为主，团队无 PG 经验） |
| 备选 B | 微信云开发数据库（NoSQL，免运维有免费额度；但订单状态机、多表关联、举报/审核队列等强关系场景用文档库是自找麻烦，且锁定厂商） |
| **理由** | ① 业务关系密集（用户-商品-会话-订单-评价-举报），关系型是必然选择；② MySQL 8 的 CTE/窗口函数/JSON 字段已够用；③ 搜索场景（F6）MVP 量级用 `FULLTEXT`/`LIKE + 联合索引`即可，不引入 Elasticsearch（N4 的 P95≤3s 口径在千级商品下毫无压力）；④ 单机 Docker 部署，主从/分库分表均不需要。 |

### 2.4 文件/图片存储

| 项 | 结论 |
|---|---|
| **选型** | **腾讯云 COS（标准存储 + CDN 域名）**，图片经服务端签名直传（小程序 `wx.uploadFile` → 后端预签名 → COS），服务端只存 URL |
| 备选 A | 七牛云（永久免费 10GB 存储 + 10GB/月流量，零预算最优；但小程序 `uploadFile/downloadFile` 合法域名配置与备案要求相同，生态文档略弱） |
| 备选 B | 阿里云 OSS（无长期免费额度，新客试用 3 个月） |
| 备选 C | 服务器本地磁盘 + Nginx（零成本但占用小带宽、无 CDN、备份麻烦，仅作兜底） |
| **理由** | ① MVP 量级估算（300 商品 × 3 图 × 压缩后 ≈300KB/图 ≈ 270MB，见 §6.3）远低于任何一家免费额度；② COS 新用户 6 个月 50GB 免费额度，过期后按量约 ¥0.1/GB/月，270MB 月成本不足 ¥0.1，实质零成本；③ 与小程序同生态，合法域名配置顺畅；④ 上传前服务端校验 MIME/大小（≤5MB/图，商品 ≤9 图），图片压缩在小程序端完成省流量。**兜底**：任何一家不可用时可切换备选 C，URL 统一走自己的域名前缀，切换不改数据库。 |

### 2.5 部署与运行环境

| 项 | 结论 |
|---|---|
| **选型** | **腾讯云轻量应用服务器 1 台（2C2G，学生/活动价 ≈¥100/年）+ Docker Compose**（容器：nginx、server(NestJS)、mysql:8、定时任务与主进程合一）；域名 1 个（≈¥55/年）+ 免费 SSL（Let's Encrypt/云厂商免费证书）；ICP 备案（免费，须预留 15-20 个工作日） |
| 备选 A | 微信云托管 CloudBase Run（免备案域名、与小程序天然互通、有免费额度；但按量计费超额度后不可控、云数据库为 MySQL 需另购、厂商锁定） |
| 备选 B | 纯免费路线：CloudBase 云托管免费额度 + 七牛云（理论上 0 元；风险是免费额度政策随时可调整，且无 SLA，见 §6.5） |
| 备选 C | Vercel/Railway 等海外平台（小程序要求已备案域名，海外节点访问不稳，直接排除） |
| **理由** | ① 单机 Docker Compose 是单人维护的复杂度下限与能力上限的最佳交点，一键重建、环境即代码；② 2C2G 跑 Node+MySQL8（限内存 512MB）足够支撑千级用户、N4 三倍并发压测；③ 云托管免费额度看似零预算，但"额度耗尽即停服"对运营中平台是不可接受风险，故**建议主路线接受约 ¥155/年的最低现金支出**——此点列入 §7 决策请求（若坚持绝对零预算则走备选 B 并接受 §6.5 风险）。 |
| CI/CD | GitHub Actions（免费）：push main → 构建镜像 → SSH 部署 → `docker compose up -d`；数据库迁移用 Prisma migrate 在部署步骤执行。 |

### 2.6 登录认证方案

| 项 | 结论 |
|---|---|
| **选型** | **小程序端：微信登录 `wx.login` → code 换 openid/unionid（code2session）→ 服务端签发 JWT（access 7 天 + refresh 30 天）**。session_key 不落库明文（仅存内存缓存短期用于解密场景，MVP 不解密敏感数据）。**管理后台：账号密码（bcrypt）+ JWT（access 2 小时）+ RBAC 两角色（审核员/管理员）**。 |
| 备选 A | 微信云开发 `wx.cloud.callFunction` 免鉴权（省 JWT 环节，但锁定云开发，与 §2.5 主路线冲突） |
| 备选 B | Session + Cookie（小程序无 Cookie 机制，排除） |
| **理由** | ① openid 是微信生态唯一稳定用户标识，免注册流程，配合 PRD 游客可浏览（N1）实现"打开即用"；② 身份认证（学号/校园邮箱/商家资质）是业务层认证，与微信登录解耦：登录只解决"你是谁（设备层）"，F1 认证解决"你有什么权限（业务层）"，两状态分字段存储（§4 user 表）；③ JWT 无状态，单机够用，无需 Redis（黑名单场景——封禁/注销——走数据库 `user.status` 每次请求校验中间件，牺牲一次主键查询换架构简单）。 |

### 2.7 管理后台前端方案

| 项 | 结论 |
|---|---|
| **选型** | **Vue 3 + Vite + Element Plus + Pinia**，普通 SPA 直接由 nginx 托管静态文件 |
| 备选 A | React + Ant Design（生态同样成熟，纯团队偏好；与小程序端技术栈无协同，故不占优） |
| 备选 B | vue-element-admin / 若依等脚手架（功能臃肿，单人项目引入大量无用代码） |
| **理由** | ① 后台 10 个页面全部是表格+表单+详情抽屉，Element Plus 组件覆盖率 100%，几乎不写自定义组件；② Vue 模板语法对 CRUD 页面开发效率最高；③ 与后端同为 TypeScript，DTO 类型可手动同步；④ 部署只是静态文件，零额外运行时。 |

### 2.8 其他关键库选型（一句话）

定时任务（F9 到期提醒、F35 超时确认、F17 评价期结束、F27 毕业处置）：NestJS `@nestjs/schedule`（进程内 cron，不引入消息队列/Redis）；违规词匹配：DFA 敏感词过滤（自建 100 行实现，词表来自 §4 word_list）；日志：pino + 按日切割文件（不引入 ELK）。

#### 模块解耦纪律（v1.2，用户三条强制原则落地）

**总则（用户拍板原文，逐字照录）**：
1. 模块边界必须清晰；
2. 解耦重要性大于复用；
3. 代码避免共享模块。

**自给自足规则**：每个模块自带自己的数据访问层（repository）、业务逻辑（service）、校验（validator/DTO 校验），**禁止为复用而抽公共业务模块**；两个模块需要相似逻辑时，允许复制后各自演化（宁可重复，不可共享实现）；唯一例外：contract 层（接口类型定义、枚举、错误码）可集中在 contract/ 目录，但**仅限声明，不含任何逻辑函数**。

**可检查执行机制（让边界可验证）**：
1. **目录约束**：`server/src/modules/<模块名>/` 下必须自含 controller/service/repository/validator 四个子层，禁止出现 modules/ 之外的共享业务目录（只允许 contract/ 与基础设施 infra/（数据库连接、日志、鉴权中间件等纯技术设施））。
2. **import 规则**：模块内文件只允许 import：本模块内部、contract/、infra/、node_modules；禁止 import 其他模块的任何文件（含 service/repository/entity）；配置 ESLint `no-restricted-imports` 规则使其 CI 可自动拦截。
3. **评审检查点**：每个开发批次交付时，CEO 核实清单包含"跨模块 import 扫描结果为零"（grep/CI 报告）。
4. **DB 层纪律维持**：禁跨 schema 直查，四 schema（auth/product/trade/chat）隔离不变。
5. 以上纪律是将来按模块拆分为微服务的切割前提，拆分候选顺序：chat-msg 优先、trade 次之。
6. 架构设计图见 `docs/design/2026-02-06-架构设计图.md`。

### 3.3 并行开工与契约纪律约定

1. **契约先行**：§5 评审通过后，`server/src/contract/` 作为唯一事实源；前端两个 `types/contract.ts` 直接拷贝同步，字段不一致由 TypeScript 编译报错暴露。
2. **Mock 并行**：契约冻结当天，后端提供 `nestjs + prism` mock 服务（按契约返回假数据），小程序与后台即可不依赖真实后端开工。
3. **枚举集中**：所有状态枚举（订单五态、商品三态、举报四结果等）只定义在 contract 层，禁止前端硬编码魔法值。
4. **页面-模块对照**：U 页面只调用户端 API（`/api/v1/...`），A 页面只调后台 API（`/admin/v1/...`），两套鉴权中间件独立。


## §4 数据库表设计草案

统一约定：MySQL 8（InnoDB / utf8mb4）；`id` 一律 `BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT`；所有表含 `created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`、`updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`（下文不再重复列出）；金额 `DECIMAL(10,2)`；枚举一律 `VARCHAR(32)` 并在注释中列值；时间 `DATETIME`。逻辑删除仅在明确需要的表上给出。

## 5. API 接口契约（草案）

> 本草案覆盖 PRD 全部 P0 功能点（P1 预留扩展位）。冻结评审另行召开，评审通过前字段可调整；通过后变更须走 CEO 决策并记入会议纪要。本节为用户端部分（§5.1 通用约定 + §5.2 用户端 API），后台管理 API 见后续委派文档（§5.3，另文补充）。

### 5.1 通用约定

**统一响应包络**

```json
{ "code": 0, "message": "ok", "data": { ... } }
```

- `code`：业务错误码，`0` 表示成功；HTTP 状态码仅表达传输层语义（200/401/429/500），业务判定一律以 `code` 为准。
- `message`：人类可读信息，失败时为可直接展示给用户的提示。
- `data`：成功时的业务数据，失败时为 `null`（风险警示等特殊场景除外，见 chat 发消息接口）。

**分页结构**（所有列表接口统一）

```json
{ "page": 1, "pageSize": 20, "total": 137, "list": [ ... ] }
```

- 请求参数统一为 `page`（默认 1）与 `pageSize`（默认 20，上限 50）。
- 游标式深分页（聊天记录等）使用 `before_id` 参数，响应不返回 `total`，改返回 `has_more`。

**错误码分段**

| 区段 | 含义 | 示例 |
|---|---|---|
| 0 | 成功 | — |
| 1xxx | 认证/权限 | 1001 未登录/token 无效；1002 token 过期；1003 无权限；1004 未通过实名认证；1005 用户已被禁用；1006 学校未开放/申请被拒绝 |
| 2xxx | 商品 | 2001 商品不存在；2002 商品已下架/已售；2003 急出打标超出 3 件上限；2004 图片数量/格式不合规；2005 库存不足 |
| 3xxx | 沟通 | 3001 会话不存在；3002 消息命中风险词需确认；3003 被拉黑无法发起会话；3004 意向卡片状态冲突 |
| 4xxx | 订单交易 | 4001 订单不存在；4002 订单状态不允许该操作；4003 锁单失败（已被他人锁定）；4004 取消响应超时；4005 现场拒收缺少时间或说明 |
| 5xxx | 评价/举报/申诉 | 5001 订单不可评价；5002 重复评价；5003 举报类型/证据缺失；5004 申诉不成立条件（无对应处罚记录） |
| 6xxx | 后台管理 | 6001 管理员无权限；6002 审核任务不存在/已被处理 |
| 9xxx | 系统 | 9001 参数校验失败；9002 频率限制；9999 系统内部错误 |

**鉴权**

- 用户端：`Authorization: Bearer <JWT>`，JWT 由微信登录（`code2session` 换取 openid/unionid 后签发）获得，有效期 7 天，刷新令牌 30 天；payload 含 `uid`、`role`（student/teacher/merchant）、`school_id`。
- 后台：独立 JWT 体系（账号密码+图形验证码登录），payload 含 `admin_id`、`perms`，与用户端 token 互不认受。
- 未认证接口（学校列表、商品列表/详情浏览）不要求 token，但携带 token 时可返回个性化字段（如是否已收藏）。

**幂等要求**：所有写操作（POST/PUT）必须支持幂等——创建类接口由客户端生成 `Idempotency-Key` 请求头（或服务端以业务唯一键去重，如订单的 `buyer_id+product_id+active`），网络重试/重复点击不产生重复记录。

## 6 关键技术风险与对策

### 6.1 微信支付资质（最高优先，阻塞上线口径）【需用户决策】

- **风险**：已核实：个人主体小程序无法通过微信认证、不能开通微信支付；2026-08 起个人主体仅支持虚拟商品支付，不适用实物二手交易。冻结 PRD 中 F34（线上支付）/F35（退款）存在落地阻塞。
- **对策选项**：
  - **A. 首期仅当面自提**：砍掉线上支付。需变更冻结 PRD 的 F34/F35 口径，走变更流程（CEO 决策+会议纪要）。交易闭环变弱，差评/纠纷取证更难。
  - **B. 线上支付降级为"线下扫码付款 + 平台订单留痕与确认"（推荐）**：`payment_record.channel='offline_scan'`，买卖双方线下微信/支付宝扫码互付，平台不经手资金，仅提供订单五态流转、付款确认、取消/超时规则；退款口径改为"线下自行协商退回 + 平台监督（纠纷走申诉 F30/F31）"。需 PRD 口径微调，改动面小、合规干净、零成本。
  - **C. 注册个体工商户主体**：注册低成本，微信认证约 300 元/年，可开通微信支付，轻微突破零预算约束。
  - **D. 第三方服务商灰色方案**：有封号与资金安全风险，**不推荐**。
- **结论**：推荐 B，**必须提请用户拍板**。数据库已按支付通道可插拔设计（`payment_record.channel` 枚举 + 状态机与通道解耦），A/B/C 任一决策均不返工，后续若升级为主体 C 可平滑接入微信支付。

### 6.2 实名认证落地强度有限【PRD 边界内说明即可】

- **风险**：无校方接口，学号只能收集、无法联网核验。
- **对策**：以校园邮箱验证码为主（edu 邮箱后缀校验 + 学校名单域名匹配 F36），学号仅收集存档；"名单 + 邮箱域名"属弱校验，叠加举报与黄牛风控（F20/F23）兜底。需在 PRD/用户协议中明示"证明强度有限"。无需用户决策。

### 6.3 图片存储成本【低风险】

- **风险**：MVP 量级约 300 商品 × 3 图 × 300KB ≈ 270MB，COS 新用户免费额度足够；超期后约几分钱/GB/月，成本可忽略。
- **对策**：上传端压缩 + 限制单商品最多 9 图；生命周期规则清理孤儿图片。无需用户决策。

### 6.4 消息通知触达受限【中风险，预期管理】

- **风险**：小程序订阅消息为一次性授权，用户不授权则订单/审核/申诉等关键节点无法触达。
- **对策**：关键节点（下单、审核结果、申诉进展）引导授权 + 提前申请服务通知模板；站内通知中心（F15）作为兜底通道。对触达率做预期管理，不承诺 100% 送达。无需用户决策。

### 6.5 零预算运维风险【中风险】

- **风险**：免费额度过期/耗尽、无备份 SLA、无专业值守。
- **对策**：每日数据库备份至对象存储生命周期桶；额度用量监控告警；准备降级预案（故障时切只读模式，保留浏览与公告）。无需用户决策。

### 6.6 域名与 ICP 备案【上线关键路径，需立即启动】

- **风险**：小程序后端必须使用 HTTPS + 已备案域名，备案周期约 2-3 周，是当前排期上的关键路径。
- **对策**：**立即启动域名注册与备案（用户行动项）**，备案期间并行推进开发；开发期用内网穿透/测试域名联调，备案完成后切换。

## 附录 A：架构形态评审（2026-02-06）

### A.1 三方案对比

| 维度 | A 保持单体 | B 模块化单体（推荐） | C 微服务起步 |
|---|---|---|---|
| 解耦达成度 | 低（模块边界全靠自律，易腐化） | ≈90%（schema 隔离 + service 接口 + 契约集中，纪律强制） | 100%（物理隔离） |
| 单人开发可行性 | 高 | 高（单进程单仓库，纪律成本一次性） | 低（多服务联调/部署/排障成本远超单人负荷） |
| 零预算可行性 | 完全满足（2C2G 单机即可） | 完全满足（部署形态不变，容器不增加） | 不满足（最小 4 服务，2C2G 单机内存占用超 50%，物理上跑不动） |
| 上线锚点影响 | 无 | 无（部署/契约/排期均不变） | 延期 3-6 周，直接威胁 2026 年 3 月上线锚点 |

### A.2 推荐理由（方案 B）

1. **解耦 ≈90% 达成**：通过 §3.1 模块解耦纪律（禁跨 schema 直查、四 schema 隔离、契约层集中）在单体内达成微服务式边界，且不付分布式税。
2. **单进程部署**：部署形态不变（单容器 + Docker Compose），运维复杂度不增加，零预算约束不破。
3. **单库事务保住订单五态一致性**：订单状态机（pending_delivery→…→completed）跨 product/order/payment 多表流转，单库事务天然保证一致性；微服务下需 Saga/分布式事务，复杂度暴涨。
4. **上线锚点不受影响**：B 是在现方案上"加纪律"，零返工；3 月中下旬上线目标不变。
5. **微服务解决的问题本项目均不存在**：微服务解决的是多团队独立交付与独立扩缩容问题；本项目为单人开发、单机部署、千级用户，两个前提均不成立。

### A.3 若用户坚持方案 C（微服务）的代价清单

- **最小拆分（4 服务）**：identity（认证/用户）/ goods（商品/求购）/ trade（订单/支付/评价）/ chat-msg（聊天/通知）。
- **简化口径**：网关用 Nginx 鉴权透传；服务间 HTTP 直连，不引入 MQ；注册中心省略（静态配置）。
- **代价**：
  1. 开发量 +40~60%，即延期 3-6 周，直接击穿 2026 年 3 月上线锚点；
  2. 容器 3 → 7+，Docker Compose 编排与联调复杂度翻倍；
  3. 服务器须升 4C8G，约 ¥400-1500/年，突破零预算约束；
  4. 现 2C2G 单机内存占用将超 50%，物理上跑不动；
  5. 无链路追踪（零预算不引入 SkyWalking/Jaeger），跨服务排障靠人工串日志；
  6. 违背"单人维护 + 零预算"两大核心约束（§1.1）。

**评审结论**：推荐方案 B（模块化单体），待用户最终拍板 A/B/C。
