## 1. 系统上下文图

```mermaid
flowchart TB
    subgraph Roles["系统角色"]
        Guest["游客<br/>(未登录)"]
        Buyer["买家"]
        Seller["卖家"]
        Merchant["商家<br/>(审核后开店)"]
        Ops["运营人员"]
    end

    subgraph System["校园二手交易平台"]
        MP["小程序端<br/>(原生 + TS)"]
        AdminWeb["管理后台<br/>(Vue3 + Element Plus)"]
        Server["后端服务<br/>(NestJS 单体)"]
    end

    subgraph Ext["外部依赖"]
        WX["微信生态<br/>登录 / 订阅消息 / 小程序宿主"]
        COS["腾讯云 COS<br/>图片存储"]
        DB[("MySQL 8<br/>业务数据")]
        OfflinePay["线下支付<br/>微信/支付宝扫码<br/>(平台不经手资金)"]
    end

    Guest -->|浏览搜索| MP
    Buyer -->|登录/下单/聊天/评价| MP
    Seller -->|发布/锁单/发货| MP
    Merchant -->|开店/批量管理| MP
    Ops -->|审核/处置/仲裁| AdminWeb

    MP -->|HTTPS /api/v1| Server
    AdminWeb -->|HTTPS /admin/v1| Server
    MP -->|图片直传/回显| COS

    Server -->|code 换 openid<br/>订阅消息下发| WX
    Server -->|读写| DB
    Server -.->|生成收款指引/留痕<br/>不经手资金| OfflinePay
    Buyer -.->|当面扫码付卖家| OfflinePay
    OfflinePay -.->|资金直达卖家| Seller
```

**说明（关键决策点）：**
1. **平台不经手资金**（方案 B 口径）：支付走线下微信/支付宝扫码，系统只做付款留痕与状态流转，规避资金牌照风险，也省去接入微信支付商户号。
2. **两套入口、一个后端**：小程序端走 `/api/v1`，后台走 `/admin/v1`，鉴权中间件独立，符合 §3.3 页面-模块对照约定。
3. **图片走 COS 直传**：后端只签发上传凭证与存 URL，图片流量不经过单体服务，降低带宽与存储压力。
4. **外部依赖收敛为四类**：微信生态、COS、MySQL、线下支付；无短信、无地图等额外依赖，保证校园项目可维护性。
5. **商家是卖家的特化角色**：复用卖家链路，仅叠加 admin 审核状态，不单独建流程。

## 2. 推荐方案 B 组件架构图（模块化单体）

```mermaid
flowchart TB
    subgraph Container["单容器部署边界（Docker Compose：app + mysql + nginx）"]
        subgraph App["NestJS 单体进程"]
            subgraph Contract["contract 层（仅声明：类型/枚举/错误码，无逻辑）"]
                CT["DTO / 枚举 / 错误码常量<br/>订单五态·商品三态·举报四结果<br/>禁止含任何逻辑函数"]
            end

            GW["Controller 网关层<br/>/api/v1（用户端） · /admin/v1（后台）<br/>JWT 鉴权 · 参数校验 · 统一异常过滤"]

            subgraph Modules["业务模块（§3.1，11 个）"]
                AuthM["auth 认证"]
                UserM["user 用户"]
                ProdM["product 商品"]
                WantM["wantbuy 求购"]
                ChatM["chat 聊天"]
                TradeM["trade/order 交易"]
                RevM["review 评价"]
                RepM["report 举报申诉"]
                AdmM["admin 后台"]
                CfgM["config 配置"]
                NtfM["notify 通知"]
            end

            Jobs["jobs 定时任务<br/>求购到期 · 48h 超时确认 · 评价期 · 毕业处置"]

            subgraph DataLayer["数据访问层（Prisma，模块自含 repository）"]
                DAO["每个模块自带 repository/service/validator<br/>仅可访问本 schema 的表<br/>禁止 import 其他模块任何文件"]
            end

            Infra["infra 基础设施（纯技术设施）<br/>数据库连接 · 日志 · 鉴权中间件"]
        end

        subgraph Schemas["MySQL 8（分 schema 隔离）"]
            S1[("auth schema<br/>user/identity/school")]
            S2[("product schema<br/>商品/求购/收藏/品类")]
            S3[("trade schema<br/>订单/评价/举报/申诉")]
            S4[("chat schema<br/>会话/消息/意向卡片")]
        end
    end

    GW --> Modules
    Modules --> CT
    Modules --> DAO
    Modules --> Infra
    NoShare["⚠ 无共享业务模块（用户三条强制原则）<br/>模块间只允许依赖 contract 声明与 infra 基础设施<br/>禁止代码级复用，相似逻辑允许复制后各自演化"]
    Modules -.- NoShare
    Jobs --> TradeM
    Jobs --> WantM
    Jobs --> RevM

    AuthM & UserM --> S1
    ProdM & WantM --> S2
    TradeM & RevM & RepM & AdmM --> S3
    ChatM & NtfM --> S4

    SplitNote["将来拆分线（虚线）<br/>① chat-msg 剥离候选：消息量大，可独立扩 WS 网关<br/>② trade 剥离候选：状态机复杂，需独立保障一致性"]
    ChatM -.- SplitNote
    TradeM -.- SplitNote
```

**说明（关键决策点）：**
1. **模块化单体而非微服务**：单人/小团队维护成本最低；模块边界即 NestJS Module，与 §3.1 一一对应，拆分线预留在模块边界上而非埋在代码里。
2. **无共享业务模块（v1.1 按用户三条强制原则修订）**：模块间只允许依赖 contract 声明与 infra 基础设施，禁止代码级复用；每个模块自含 controller/service/repository/validator 四个子层；相似逻辑允许复制后各自演化（宁可重复，不可共享实现）；跨模块 import 由 ESLint `no-restricted-imports` 在 CI 自动拦截，CEO 批次验收核实"跨模块 import 扫描结果为零"；所有状态枚举集中在 contract 层（仅声明，无逻辑函数），前端拷贝同步，禁止硬编码魔法值。
3. **分 schema 提前隔离**（auth / product / trade / chat）：单库内逻辑隔离，既保留跨表 join 的事务便利，又为将来按 schema 拆库拆服务扫清数据耦合。
4. **定时任务内嵌 jobs 目录**：F35 超时确认（48h）、取消默认同意（24h）、评价期、求购到期均由进程内 cron 驱动，不引入独立调度器。
5. **拆分候选标注**：chat-msg（消息体量与 WS 长连接）与 trade（状态机与一致性要求）是最可能的剥离对象，拆分线以虚线标注，触发条件（如 DAU/消息量阈值）另立决策记录。

## 3. 核心交易链路时序图（线下支付模式主链路）

```mermaid
sequenceDiagram
    autonumber
    actor B as 买家
    participant MP as 小程序端
    participant SV as 后端服务<br/>(chat/trade 模块)
    actor S as 卖家

    B->>MP: 商品页发起会话
    MP->>SV: POST /conversations
    SV-->>S: 新会话通知(订阅消息/站内)
    B->>SV: 协商(消息+意向卡片)
    SV-->>S: 消息推送
    S-->>SV: 回复协商

    Note over B,S: 达成意向，创建订单锁单
    B->>SV: POST /orders {skuId, price}
    SV->>SV: 事务: 校验商品在售<br/>UPDATE product SET status=LOCKED<br/>WHERE status=ON_SALE (防超卖)<br/>订单进入 PENDING_PAY
    SV-->>S: 锁单通知(24h 响应计时启动)
    SV-->>B: 订单创建成功+卖家收款码指引

    Note over B: 线下当面交易
    B->>S: 微信/支付宝扫码付款<br/>(平台不经手资金)
    B->>SV: 标记已付款(上传凭证可选)
    SV->>SV: 订单: PENDING_PAY -> PAID_MARKED
    SV-->>S: 买家已标记付款提醒

    S->>B: 当面交货
    B->>SV: 确认收货
    SV->>SV: 订单: PAID_MARKED -> COMPLETED<br/>商品置已售
    SV-->>S: 交易完成通知

    Note over B,S: 48h 内双方互评，延迟公开<br/>超时未评价默认好评(F17)
    B->>SV: 评价卖家
    S->>SV: 评价买家
    SV->>SV: 双方均提交/评价期届满后<br/>同步公开双方评价

    alt 超时自动确认 (F35: 48h 未确认)
        SV->>SV: jobs 扫描: PAID_MARKED 超 48h<br/>自动确认收货 -> COMPLETED
        SV-->>B: 系统自动确认通知
        SV-->>S: 交易完成通知
    end

    alt 取消分支 (F35)
        B->>SV: 发起取消申请
        alt 卖家 24h 内未响应
            SV->>SV: jobs 扫描: 默认同意取消<br/>订单 -> CANCELLED, 商品解锁回在售
        else 卖家同意
            S-->>SV: 同意取消
            SV->>SV: 订单 -> CANCELLED, 商品解锁
        else 卖家拒绝
            S-->>SV: 拒绝取消(进入协商/可申诉)
            SV-->>B: 取消被拒通知
        end
        SV-->>B: 取消结果通知
    end

    alt 拒收分支
        B->>SV: 当面验货后拒收
        SV->>SV: 订单 -> CANCELLED(拒收)<br/>商品解锁回在售<br/>记录拒收原因供申诉
        SV-->>S: 拒收通知(可发起申诉)
    end
```

**说明（关键决策点）：**
1. **防超卖靠行级条件更新**：创建订单在单事务内执行 `UPDATE ... WHERE status=ON_SALE`，影响行数为 0 即抢单失败，不引入分布式锁（方案 B 单机口径足够）。
2. **订单五态落地**：`PENDING_PAY → PAID_MARKED → COMPLETED / CANCELLED`（含取消与拒收两个取消入口），状态枚举只定义在 contract 层。
3. **付款是"留痕"而非"清算"**：买家标记已付款仅推进状态机并通知卖家核验，平台不校验真实资金流，申诉时以留痕凭证+聊天记录为仲裁依据。
4. **两条超时规则由 jobs 兜底**：取消申请 24h 未响应默认同意、标记付款后 48h 未确认自动收货，均由进程内 cron 实现，不依赖客户端行为。
5. **评价延迟公开**：双方均提交或评价期届满后才互相可见，超时默认好评（F17），抑制报复性差评。
