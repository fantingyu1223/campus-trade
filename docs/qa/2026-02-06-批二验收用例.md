## 1. 范围与依据

- 测试范围：批二·闭环功能 —— F9 求购专区（P0）、F12 站内沟通（P0）、F13 防诈骗提示（P0）、F14 交易意向确认（P1）、F34 双模式交易流程（P0）、F35 交易取消/拒收与超时确认（P0）、F17 交易评价（P0）、F15 消息通知（P1）。
- 依据文档：
  - PRD：`docs/prd/2026-02-06-校园二手平台完整PRD.md` §5.2（F9）、§5.3（F12/F13/F14/F15/F34/F35）、§5.4（F17）的 F#-AC# 验收标准，§7.2 口径裁决第 1/2/3/4/6/8 条，§8.1 风险词表。
  - 接口契约：`docs/design/2026-02-06-技术选型与总体方案.md` §5.1 统一响应与错误码表、§5.2 用户端 API（#20-24 want-buy、#25-29 chat、#30-37 order、#38-39 review、#44-45 notification）、§4.17-4.20 订单/评价表。
- 覆盖率口径：P0 功能 AC 逐条映射、覆盖率 100%；F14/F15（P1）同步覆盖。共 21 条 AC、40 条用例。
- 关键错误码（契约 §5.1）：3001 会话不存在、3002 命中风险词需确认、3004 意向卡片状态冲突、4001 订单不存在、4002 订单状态不允许该操作、4003 锁单失败（已被他人锁定）、4004 取消响应超时、4005 现场拒收缺少时间或说明、5001 订单不可评价、5002 重复评价、9001 参数校验失败、1003/1004 权限类。

## 2. 公共约定与测试数据

- 测试账号（沿用批一）：`stu_a`（卖家）、`stu_b`（买家）、`stu_c`（第二买家，并发/对照用）、`teacher_a`、`user_new`（未认证）。
- 基础数据：在售商品 P10（卖家 stu_a，线上支付意向）、P11（卖家 stu_a，仅线上支付声明，用于 F34-AC4）、已下架商品 P12、已售商品 P13；风险词表已加载 §8.1（高危「先转账」、中危「加微信详聊」）。
- 时间类用例约定：24h/48h/27 天/30 天/7 天等计时场景，一律通过**测试钩子**（直接改写库中 `respond_deadline`/`timeout_deadline`/`expire_at`/`review_deadline` 或调用测试环境时间加速接口后手动触发 cron）构造边界时刻，禁止真实等待。
- 留痕断言约定：凡 PRD 要求留痕的（order_event、风险警示、拒收记录），API 用例须断言留痕记录存在且关键字段齐全。
- 状态语义映射：PRD 五态 待交货/待确认/已完成/已取消/申诉中；契约订单五态 `pending_pay/paid/completed/cancelled/rejected`，用例中按语义对应断言（差异见 §7 遗留风险 R1）。
- 断言风格：API 用例断言业务 code + 关键字段 + 留痕；UI 用例断言页面可见元素与跳转。

**Q2-F9-01 发布求购后出现匹配商品，求购者收到撮合提示**
- 前置条件：`stu_b` 已认证；分类「教材/教辅」存在。
- 步骤：① `stu_b` POST `/want-buys`（title=求购高等数学（下）、max_price=20、category_id=教材、成色要求=九成新）；② `stu_c` POST `/products` 发布匹配商品（同分类、title 含「高等数学（下）」、price=15 ≤ max_price）；③ 触发撮合任务后 `stu_b` GET `/notifications?type=want_buy_match`。
- 预期结果：① 返回 `id`、`expire_at`（=发布时间+30 天，PRD 口径）；③ 通知列表新增 `type=want_buy_match` 一条，`payload` 含匹配商品 `product_id`。

**Q2-F9-02 卖家侧可见相关求购并可主动联系**
- 前置条件：`stu_b` 的求购 W1 处于 active；`stu_a` 有同分类在售商品。
- 步骤：① `stu_a` GET `/want-buys?scope=all&category_id=教材`；② 从 W1 详情向 `stu_b` 发起会话（POST 会话创建）。
- 预期结果：① 列表含 W1（字段含 title/max_price/expire_at）；② 会话创建成功，W1 求购者侧收到新会话（联动 Q2-F12-01 未读断言）。

**Q2-F9-03 求购第 27 天收到到期前 3 天提醒**
- 前置条件：W2 求购发布于 T0，`expire_at=T0+30天`。
- 步骤：时间钩子推进至 T0+27 天（或将 `expire_at` 改写为当前+3 天），手动触发求购到期提醒 cron；`stu_b` GET `/notifications?type=want_buy_expire`。
- 预期结果：第 27 天产生一条求购到期提醒通知（`type=want_buy_expire`，payload 含求购 id 与剩余天数=3）；第 26 天触发不产生（边界对照）。

**Q2-F9-04 求购第 30 天未续期失效并停止撮合（必含异常路径）**
- 前置条件：W3 求购发布于 T0，期间未续期。
- 步骤：① 时间钩子推进至 T0+29 天 23:59，GET `/want-buys?scope=mine` 确认 W3 仍 active；② 推进至 T0+30 天整，触发到期 cron；③ GET `/want-buys?scope=all` 与 `scope=mine`；④ 由 `stu_c` 新发布匹配商品，观察是否再产生撮合通知。
- 预期结果：① 第 30 天前 W3 仍有效；② 到期后 W3 `status=expired`；③ 求购大厅列表不再出现 W3；④ 不再产生任何 `want_buy_match` 通知（通知数与步骤③前一致）。

**Q2-F9-05 手动关闭求购后立即停止一切撮合通知**
- 前置条件：W4 求购 active。
- 步骤：① `stu_b` POST `/want-buys/{W4}/close`；② `stu_c` 发布匹配商品；③ `stu_b` GET `/notifications?type=want_buy_match`；④ GET `/want-buys?scope=all`。
- 预期结果：① 返回 `status=closed`；③ 无新增撮合通知；④ 大厅列表不含 W4。

**Q2-F9-06 标记"已买到"后停止撮合且不再出现在求购列表**
- 前置条件：W5 求购 active。
- 步骤：① POST `/want-buys/{W5}/bought`；② 发布匹配商品触发撮合任务；③ GET `/want-buys?scope=all`。
- 预期结果：① 返回 `status=bought`；② 无撮合通知；③ 列表不含 W5。

**Q2-F9-07 续期不限次数、每次延长 30 天（口径裁决 §7.2-6）**
- 前置条件：W6 求购 active，`expire_at=E0`。
- 步骤：① POST `/want-buys/{W6}/renew`，记录新 `expire_at=E1`；② 连续再续期 2 次（共 3 次）；③ 非本人 `stu_a` 尝试对 W6 续期。
- 预期结果：① E1=E0+30 天；② 第 2、3 次续期均成功，每次在上次基础上 +30 天（无次数上限拦截）；③ 被拦截，code=1003。

**Q2-F12-01 联系卖家→卖家会话未读→阅读后买家侧已读**
- 前置条件：P10 在售（卖家 `stu_a`）；`stu_b` 与 `stu_a` 无既有会话。
- 步骤：① `stu_b` 从 P10 详情发起会话并 POST `/chats/{conv_id}/messages`（content=「还在吗」）；② `stu_a` GET `/chats`；③ `stu_a` GET `/chats/{conv_id}/messages`（阅读动作）；④ `stu_b` GET 消息列表；⑤ UI 核对卖家会话列表未读角标与买家侧已读标识。
- 预期结果：① 返回 `msg_id`、`risk_level=0`；② 卖家会话列表出现该会话且 `unread≥1`；③ 阅读后卖家 `unread=0`；④ 买家侧该消息为已读状态；⑤ UI 未读角标出现→消失、买家侧显示「已读」。

**Q2-F12-02 已下架商品无既有会话者发起新会话被拦截**
- 前置条件：P12 已下架；`stu_c` 与卖家无关于 P12 的会话。
- 步骤：`stu_c` 从 P12 详情发起会话（POST 会话创建）。
- 预期结果：被拦截，code=2002（或契约约定的会话创建拦截码），message 提示商品已下架；会话列表无新会话。

**Q2-F12-03 已售商品无既有会话者发起新会话被拦截**
- 前置条件：P13 已售；`stu_c` 与卖家无关于 P13 的会话。
- 步骤：`stu_c` 从 P13 详情发起会话。
- 预期结果：被拦截，code=2002，提示商品已售；既有会话的买卖双方（stu_a/stu_b）原会话仍可查看历史消息（留痕不受损，N9）。

**Q2-F13-01 命中风险词且 confirm_risk=false/缺省时发送被拦截（必含异常路径）**
- 前置条件：`stu_b` 与 `stu_a` 存在会话 C1。
- 步骤：POST `/chats/{C1}/messages`，`type=text`、`content=「先转账再发货」`，不传 `confirm_risk`（或显式 false）。
- 预期结果：code=**3002**；`data` 仍返回风险详情：`risk_level=1`（高危词可约定为更高档）、`risk_words[]` 含「先转账」；消息**未**入库（GET 消息列表无该条）。

**Q2-F13-02 命中风险词后 confirm_risk=true 放行发送并留痕（必含异常路径）**
- 前置条件：同 C1；上一用例消息未入库。
- 步骤：① 同一内容重发，`confirm_risk=true`；② 查询风险警示留痕记录（测试钩子直查 risk 留痕表/运营侧调阅接口）。
- 预期结果：① 发送成功，返回 `msg_id`、`risk_level=1`、`risk_words[]`；② 留痕记录存在且五字段齐全：**发送人、接收人、命中词（先转账）、时间、消息原文**；接收侧消息可见且附带安全提示条标记（API 侧 `risk_level>0` 供前端渲染）。

**Q2-F13-03 未命中风险词的消息正常发送且零留痕**
- 前置条件：同 C1；发送前记录留痕表行数 N0。
- 步骤：POST `/chats/{C1}/messages`，content=「明天东门见」，`confirm_risk` 不传。
- 预期结果：直接发送成功（code=0），`risk_level=0`、`risk_words=[]`；留痕表行数仍为 N0（未命中不产生留痕，§7.2-1）。

**Q2-F13-04 付款前强制展示资金安全提示弹层**
- 前置条件：`stu_b` 对 P10 创建订单成功，进入付款页。
- 步骤：UI 进入线上支付付款页，观察弹层；不点确认尝试付款；点击确认后付款。
- 预期结果：付款前强制弹层展示「平台不托管资金，务必当面验货后再确认收货」及取消/拒收规则摘要；未确认前付款按钮不可用/被拦截；确认后方可发起付款。

**Q2-F13-05 聊天页与发布页常驻安全提示条**
- 前置条件：`stu_b` 已登录。
- 步骤：UI 分别打开会话聊天页、商品发布页。
- 预期结果：两页均在固定位置展示常驻安全提示条（文案含防诈骗提示），不因滚动/操作消失。

**Q2-F14-01 意向卡片发起→待确认→对方确认→双方已确认并留痕**
- 前置条件：`stu_b` 与 `stu_a` 存在会话 C1，商品 P10 在售。
- 步骤：① `stu_b` POST `/chats/{C1}/intent`（product_id=P10、price=15、trade_point=东门、trade_time=明天 14:00）；② `stu_a` 查看会话消息确认卡片状态；③ `stu_a` POST `/chats/intents/{intent_id}/respond`，`action=accept`；④ 双方查看会话。
- 预期结果：① 返回 `intent_id`、`status=pending`；② 对方确认前卡片保持待确认；③ 返回 `status=confirmed`（双方已确认）且生成 `order_id`；④ 意向卡片在会话中留痕（消息列表可见卡片消息含确认状态与时间）。

**Q2-F14-02 意向卡片被拒绝与重复响应冲突拦截**
- 前置条件：`stu_b` 已发起意向卡片 I2（pending）。
- 步骤：① `stu_a` POST respond，`action=reject`；② 任一方再次对 I2 respond。
- 预期结果：① 卡片 `status=rejected` 并留痕，不生成订单；② 被拦截，code=**3004**（意向卡片状态冲突）。

**Q2-F34-01 线上支付付款成功→商品锁定交易中→订单待交货→他人付款入口关闭**
- 前置条件：P10 在售，无进行中订单。
- 步骤：① `stu_b` POST `/orders`（product_id=P10，带 `Idempotency-Key`）；② 模拟付款成功回调/确认；③ GET `/products/{P10}` 与 GET `/orders/{order_id}`；④ `stu_c` 打开 P10 详情/尝试创建订单。
- 预期结果：① 返回 `order_id`、`order_no`、`status=locked/pending_pay`、`pay_deadline`、`countdown_sec`；② 付款成功后订单进入待交货语义态（`paid`），商品锁定为「交易中」；④ `stu_c` 付款入口关闭：POST `/orders` 返回 code=**4003**（已被他人锁定）或 2002。

**Q2-F34-02 同一商品两人同时付款防超卖，仅一单成功（必含异常路径）**
- 前置条件：新在售商品 P14（卖家 stu_a），无进行中订单。
- 步骤：`stu_b` 与 `stu_c` 以不同 `Idempotency-Key` **并发** POST `/orders`（product_id=P14），随后双方均尝试完成付款确认。
- 预期结果：两个创建请求中**仅一个**成功（code=0），另一个返回 **4003**；付款阶段同样仅一单可达 `paid`；GET `/orders?role=buyer` 核对 P14 全平台仅存在一条有效订单；无脏数据（商品「交易中」仅绑定成功方订单）。

**Q2-F34-03 当面自提：线下付款+卖家标记已售指定买家→订单完成→买家获评价入口**
- 前置条件：新在售商品 P15；`stu_b` 与卖家协商为当面自提。
- 步骤：① 线下付款后 `stu_a` POST `/products/{P15}/sold`，`buyer_id=stu_b`（自动生成线下订单）；② GET `/orders/{order_id}`；③ `stu_a` POST `/orders/{order_id}/complete-offline`（或标记已售即完成，以契约状态为准）；④ `stu_b` 查看订单。
- 预期结果：① 返回 `order_id`；③ 订单 `status=completed`、返回 `review_pending`（双方）；④ 买家侧出现评价入口（订单详情含可评价标记）；order_event 留痕完整（创建→完成）。

**Q2-F34-04 订单状态仅允许五态内按规则流转，非法流转被拦截**
- 前置条件：存在订单 O1（pending_pay）、O2（completed）。
- 步骤：① 对 O1 直接 POST `/orders/{O1}/confirm-receive`（跳过付款）；② 对 O2 POST `/orders/{O2}/cancel`；③ 对 O2 POST `/orders/{O2}/confirm-receive`（重复流转）；④ GET `/orders/{id}` 核对响应状态枚举。
- 预期结果：①②③ 均被拦截，code=**4002**；④ 所有订单响应中 `status` 仅出现于五态枚举集合（契约：pending_pay/paid/completed/cancelled/rejected；PRD 语义：待交货/待确认/已完成/已取消/申诉中），无其他状态值；所有成功流转均写 order_event。

**Q2-F34-05 声明"仅线上支付"商品经双方一致同意可按当面自提完成**
- 前置条件：P11 发布时声明仅线上支付；`stu_b` 与 `stu_a` 会话中已确认意向卡片（trade_point 当面自提，§7.2-2：以会话内双方确认记录为准）。
- 步骤：双方按当面自提流程完成交易（标记已售指定买家 / complete-offline）。
- 预期结果：交易允许完成，订单 `status=completed`；意向声明不强制拦截；会话内最后一条双方确认记录与订单留痕一致。

**Q2-F34-06 申诉中冻结评价入口、已完成状态不可逆（§7.2-8）**

## 7. 契约差异与遗留风险（执行前需开发/架构澄清）

- **R1 订单状态枚举不一致**：PRD F34-AC3 五态为「待交货/待确认/已完成/已取消/申诉中」，契约 §5.2 #31 为 `pending_pay/paid/completed/cancelled/rejected`（无申诉中、含拒收终态），契约 §4.17 又为 `pending_delivery/pending_confirm/...`。用例暂按 PRD 语义+契约字段映射断言，若实现口径未定将阻塞 Q2-F34-04、Q2-F34-06、Q2-F35 全组。建议架构裁决统一枚举。
