## PSM-01 BC → NestJS 模块映射表

> 模块即 `server/src/modules/<模块名>/`，每模块自含 controller/service/repository/validator（§3.1 纪律）；BC 与模块不一一改名，模块沿用 §3.1 命名。

| PSM 编号 | PIM 限界上下文 | 承载模块（§3.1） | 映射方式与裁决标注 |
|---|---|---|---|
| PSM-01-1 | PIM-BC-01 身份与准入 | **auth**（登录/token/认证/注销；**商家入驻申请用户侧提交归属 auth 模块**——暂定，契约评审会确认；§5.2 merchant 分组 #7-9 由 auth 模块实现）、**user**（档案/主页/拉黑） | 一对二：auth 管"能不能进来"，user 管"对外呈现"；账号处置的写入口在 admin 治理子域，经 contract 声明接口回写（见 PSM-01-5） |
| PSM-01-2 | PIM-BC-02 商品与供给 | **product**（商品/收藏/急出）、**wantbuy**（求购/撮合） | 品类正面清单的业务读取经 config 只读快照（见 PSM-01-6），不跨模块 import |
| PSM-01-3 | PIM-BC-03 沟通 | **chat** | 一一对应 |
| PSM-01-4 | PIM-BC-04 交易履约 | **order** | 一一对应；定时流转由 `server/src/jobs/` cron 驱动（超时确认/取消默认同意），job 只调 order 模块 service |
| PSM-01-5 | PIM-BC-05 信任与治理 | **review**（评价）、**report**（举报/申诉用户侧提交）、**admin 模块内 governance 治理子域目录**（举报处置/申诉仲裁/黄牛复核/风控复核） | admin 一对二按 CEO 暂定裁决落地：**同一 admin 模块内拆 `governance/`（治理子域）与 `support/`（配置子域）两个子域目录**，目录级边界 + ESLint no-restricted-imports 检查，不拆模块——暂定，契约评审会确认。**report 写、admin 改的跨模块状态推进（C-5）通过 contract 声明接口完成**：admin/governance 不 import report 模块任何文件，仅以 contract 中的 DTO/枚举 + 进程内事件衔接（见 §4 事件映射）——暂定，契约评审会确认 |
| PSM-01-6 | PIM-BC-06 运营支撑 | **admin 模块 support 配置子域目录**（名单/词表/品类/账号管理、留痕查询，对应 §5.3 school/account/config/log/dashboard/zone 分组）；**config、notify 不作为业务模块，下沉为 infra 级只读/触达服务**（`server/src/infra/config-snapshot`、`infra/notify-sender`）——暂定，契约评审会确认 | config 承载词表/品类清单的只读快照分发（C-2 横切），notify 承载各领域事件的通知投递（C-3）；两者无业务聚合、无业务路由，仅供各模块注入调用，符合"解耦大于复用"（快照复制，不共享业务对象） |

**落地后的模块目录对照（§3.2 口径微调）**：

```
server/src/modules/
├── auth/ user/ product/ wantbuy/ chat/ order/ review/ report/
├── admin/
│   ├── governance/   # 治理子域：report 处置、appeal 裁决、violation/risk 复核、merchant-review（暂定）
│   └── support/      # 配置子域：school/account/config/log/dashboard/zone（暂定）
server/src/infra/
├── config-snapshot/  # 词表/品类只读快照（原 config 模块下沉，暂定）
└── notify-sender/    # 通知投递（原 notify 模块下沉，暂定）
server/src/contract/  # 唯一跨模块共享层：DTO/枚举/错误码/事件契约声明（无逻辑）
server/src/jobs/      # cron：求购到期、超时确认、取消默认同意、评价期、毕业处置
```

## PSM-02 聚合 → 数据表映射表（10 聚合 → 28 表全覆盖）

> **Schema 分配说明**：技术方案 §4 未逐表指定所属 schema，仅规定四 schema（auth/product/trade/chat）隔离。下表 schema 列为 **PSM 推定分配（待架构师确认）**，分配原则：表随其写入模块归属最近 schema；治理/运营类无专属 schema，就近挂 trade/product。

| PSM 编号 | PIM 聚合 | MySQL 表（§4） | schema（推定） | 写入模块 | 说明 |
|---|---|---|---|---|---|
| PSM-02-1 | PIM-AG-01 账号与认证 | `user`（status/identity_type/清仓与注销字段组）、`identity_verification` | auth | auth | user 表同时承载 AG-02 公开档案字段，按字段组切分读写责任，不拆表 |
| PSM-02-2 | PIM-AG-02 用户档案 | `user`（nickname/avatar_url/bio/real_name_masked）、`block` | auth | user | 拉黑单向边落 block 表 |
| PSM-02-3 | PIM-AG-03 商品 | `product`、`product_image`、`favorite` | product | product | Favorite 为聚合内弱实体，落独立表（uk_user_product 防重），收藏计数冗余于 product.favorite_count |
| PSM-02-4 | PIM-AG-04 求购 | `want_buy` | product | wantbuy | 撮合匹配为读模型投影，不落表 |
| PSM-02-5 | PIM-AG-05 会话 | `conversation`、`message`、`trade_intent`、`message_risk_log` | chat | chat | RiskWordHit 值对象落 message_risk_log（未命中不留痕，稀疏表）；意向卡片落 trade_intent，"最后一条双方确认"由查询口径保证 |
| PSM-02-6 | PIM-AG-06 订单 | `trade_order`、`order_event`、`payment_record` | trade | order | 聚合根三表经典映射：状态在 trade_order.status，留痕在 order_event（只增不改），资金留痕在 payment_record（通道可插拔） |
| PSM-02-7 | PIM-AG-07 评价 | `review` | trade | review | 同一订单双方两条记录，uk_order_reviewer 约束"每人每单限评一次" |
| PSM-02-8 | PIM-AG-08 举报 | `report`（evidence_urls JSON 承载 ReportEvidence） | trade | report（写）+ admin/governance（改，经 contract，暂定） | 证据不单独建表，JSON 数组承载；reporter_id 仅存表内，API 输出层剥离（匿名） |
| PSM-02-9 | PIM-AG-09 申诉 | `appeal`（evidence_urls JSON 承载 AppealEvidence） | trade | report（写）+ admin/governance（裁决，经 contract，暂定） | 同 PSM-02-8 的跨模块状态推进纪律 |
| PSM-02-10 | PIM-AG-10 商家入驻申请 | `merchant_application`、`merchant_ban_list` | auth | auth（用户侧提交，暂定）+ admin/governance（审核侧） | 禁入驻名单随聚合归入 auth schema，入驻校验三路命中（user_id/license_no/phone） |
| PSM-02-11 | BC-06 支撑表（无聚合） | `school`、`school_join_application` | auth | admin/support 写、auth 读 | 名单读侧经 config-snapshot |
| PSM-02-12 | 同上 | `category`、`word_list`、`risk_warning` | product | admin/support 写、config-snapshot 分发读 | risk_warning 规则扫描 product 表触发，就近挂 product schema |
| PSM-02-13 | 同上 | `violation_intercept_log` | chat | chat/product/wantbuy 各场景写入（infra 拦截器） | 跨场景留痕表，挂 chat schema 推定；各模块只写不互相读 |
| PSM-02-14 | 同上 | `admin_user`、`admin_operation_log`、`notification` | trade | admin/support、infra/notify-sender | 治理/留痕/通知无自然 schema，就近挂 trade（推定）；notification 由 notify-sender 统一写入 |

> **覆盖核对**：28 表 = PSM-02-1~10 聚合表 17 张 + PSM-02-11~14 支撑表 11 张，无遗漏、无跨 schema 共享表。

## PSM-03 状态机 → 枚举/表字段映射

### PSM-03-1 PIM-SM-01 订单状态机 → `trade_order.status` + `order_event` + contract `OrderStatus` 枚举

| PIM 状态/迁移 | 落点 |
|---|---|
| 待交货 / 待确认 / 已完成 / 已取消 / 申诉中 | `trade_order.status`：`pending_delivery` / `pending_confirm` / `completed` / `cancelled` / `appealing`（§4.17）；contract 枚举权威定义以此为准 |
| 取消请求中（态内子状态） | **不立枚举值**，以字段组承载：`cancel_initiator_id` + `cancel_requested_at` + `cancel_deadline`（+24h）+ `cancel_reason` + `cancel_reject_note`；拒绝取消即清空字段组并写 order_event |
| 全部迁移留痕 | `order_event(from_status, to_status, actor[buyer/seller/system/admin], note)`，只增不改 |
| 超时自动确认 / 取消默认同意 | `timeout_deadline`（meet_time+48h 或建单+48h）、`cancel_deadline`，由 `server/src/jobs/` cron 扫描（索引 idx_status_deadline / idx_cancel_deadline） |
| 触发接口 | §5.2 #30 创建、#32 confirm-receive、#33 cancel、#34 cancel/respond、#35 reject-onsite、#36 complete-offline；#13 products/{id}/sold（标记已售联动）；后台 #67 adjudicate（进出申诉中的结案侧） |

⚠️ **不一致 PSM-INC-01（上报，不裁决）**：§5.2 #31 注释给出的五态为 `pending_pay/paid/completed/cancelled/rejected`，与 §4.17 表枚举（pending_delivery/pending_confirm/completed/cancelled/appealing）及 PRD F34 AC3（待交货/待确认/已完成/已取消/申诉中）**三方口径不一致**，且 §5.2 多出 `rejected` 终态而表枚举无此值（#35 reject-onsite 返回 `status:rejected` 无处落库）。本模型以 §4.17 + PRD 为准落模，契约评审会须裁决统一。

### PSM-03-2 PIM-SM-02 商品状态机 → `product.status`

| PIM 状态 | 表枚举（§4.8） | 迁移驱动 |
|---|---|---|
| 上架 / 下架 / 交易中 / 已售 | `on_sale` / `off_sale` / `trading` / `sold` | #10 发布上架、#12 offline、付款成功→trading（EV-02 副作用）、订单取消→回 on_sale（EV-05）、订单完成/#13 标记已售→sold |
| 已售必录指定买家 | `sold_buyer_id` + `sold_at`（NOT NULL 由应用层守卫） | #13 强制 `buyer_id` |

### PSM-03-3 PIM-SM-03 求购状态机 → `want_buy.status`

| PIM 状态 | 表枚举（§4.11） | 迁移驱动 |
|---|---|---|
| active / closed / bought / expired | 同名四值 | #20 发布、#21 renew（`renewed_count`+`expire_at` 顺延）、#22 close、#23 bought；expired 由 jobs cron 扫描 `idx_status_expire` |
| 第 27 天到期提醒 | 不落状态，cron 触发 EV-12 → notification | — |

⚠️ **不一致 PSM-INC-02（上报）**：§5.2 #20 `expire_days 默认 7`、#21 `续期延长 7 天`，与 §4.11 `expire_at = 发布+30 天、续期+30 天` 及 PRD CIM-R-33（30 天）冲突。本模型以 §4.11 + PRD 为准，契约待改。

### PSM-03-4 PIM-SM-04 商家入驻申请状态机 → `merchant_application.status` + SLA/冷却字段组

| PIM 状态/机制 | 落点 |
|---|---|
| 待审核、审核中 | **合并落 `pending`**（取舍：受理不单独落状态值，SLA 计时不受影响的展示差异由 `reviewer_id` 是否已分配派生） |
| 通过 / 驳回 | `approved` / `rejected`，驳回必带 `reject_reason_code`（8 枚举）+ `reject_reason_detail` |
| 冷却中（驳回后子状态） | 不立枚举值，`cooldown_until = reviewed_at + 7 天` 字段承载，提交时校验 |
| SLA 2 工作日跳节假日 | `submitted_at` + `sla_deadline`，超时仅标记（jobs 扫描 idx_status_sla） |
| 触发接口 | 用户侧 #7/#8/#9（auth 模块承载，暂定）；审核侧 #61-64（admin/governance） |

⚠️ **不一致 PSM-INC-03（上报）**：① §4.5 表枚举含 `cancelled`（用户撤回）终态，PIM-SM-04 未建模"撤回"，需裁决是否回填 PIM；② 表枚举无"审核中"独立值（本模型按合并取舍，见上）；③ §5.3 #64 驳回理由用数字码 1-8，§4.5 用字符串枚举（license_invalid 等），编码口径与语义顺序不一致，契约评审会统一。

### PSM-03-5 PIM-SM-05 评价状态机 → 派生，不落独立状态字段（取舍）

| PIM 状态 | PSM 承载方式 |
|---|---|
| 不可评 / 可评 | 由 `trade_order.status = completed` + `completed_at + 7 天`（即 `review.review_deadline`）派生，不冗余存储 |
| 单方已评待公开 | `review.is_public = 0` 且对方无记录 |
| 已公开 | `is_public = 1` + `public_at`；双方均提交立即公开，单方到期由 jobs cron 公开（idx_deadline） |
| 默认好评 | `is_default = 1, rating = 5, content = NULL`（窗口届满补全，非状态） |
| 入口冻结 | 由 `trade_order.status = 'appealing'` 派生（提交评价接口 #38 前置校验），结案后自动恢复；**窗口不顺延**（承 PIM D-2 取舍） |

| PIM-EV-01 订单已创建 | #30 POST `/orders`；当面自提路径 #29 intents respond accept | `order_status` → 买卖双方 |
| PIM-EV-02 买家已付款 | MVP 线下通道：payment_record 置 paid 由 #30 锁单/线下确认流程写入（线上支付 P1 预留，#30 已留 channel 字段） | `order_status` → 卖家（备货交货提醒） |

| PIM-EV-04 订单已完成 | #32 confirm-receive / #36 complete-offline / #13 products sold / jobs 超时自动确认 | `order_status` + `review_remind` → 双方（开启互评窗口） |

| PIM-EV-13 举报已提交 | #40 POST `/reports`（report 模块写） | `report_result` → 举报人（提交回执，复用枚举）；进 admin/governance 队列（#54） |

## PSM-05 PIM→PSM 转换取舍记录

1. **事件机制降级为进程内事件 + notification 表**：PIM 的 15 个领域事件在 MVP 以 NestJS 进程内同步事件/模块内编排实现，通知触达落 `notification` 表（§4.28 本就允许"MQ 或本地事件表"），不引入消息队列——与模块化单体部署一致；事件契约（名称/载荷）仍集中在 `contract/` 声明，为将来拆微服务（chat 优先、trade 次之）保留升级通道。
2. **态内子状态字段化，不扩枚举**：订单"取消请求中"、入驻申请"冷却中"不立状态枚举值，以字段组（cancel_* 五字段、cooldown_until）承载，保持 trade_order.status 五态、merchant_application.status 四态与契约枚举最小化。
3. **评价状态机整体派生化**：PIM-SM-05 五态不落 status 字段，由 order.status + review 字段组（is_public/is_default/review_deadline/public_at）派生，消除双写不一致风险；代价是状态判定逻辑集中在 review service，需以单测锁定口径。
4. **横切配置下沉 infra 快照（暂定裁决落地）**：词表/品类清单由 `infra/config-snapshot` 只读快照分发，各模块启动加载+变更失效，是唯一合法的跨 schema 读通道（四 schema 隔离下 product 发布校验与 chat 风险词校验均需词表，快照复制取代共享表，承 C-2"宁可复制不可共享"）。
5. **admin 不拆模块、拆子域目录（暂定裁决落地）**：治理/配置两子域以 `admin/governance`、`admin/support` 目录边界 + ESLint import 规则承载，子域间同样禁互相 import；将来若裁决拆模块，目录即迁移单元。
6. **商家入驻双端落点**：用户侧提交（#7-9）归 auth 模块（暂定裁决），审核侧（#61-64）归 admin/governance，两侧经 contract 声明 + merchant_application 表（auth schema）衔接——admin/governance 对该表的写经由 contract 接口委托 auth 模块执行，不跨 schema 直写（暂定，契约评审会确认）。
7. **Schema 逐表分配为 PSM 推定**：§4 未指定 28 表与四 schema 的对应关系，本模型按"表随写入模块就近归属"推定（见 §PSM-02 表头说明），治理/运营类表（admin_user/admin_operation_log/notification/violation_intercept_log）的归属尤需架构师确认。
8. **弱实体与证据不建表**：Favorite 落独立表（有唯一约束与计数诉求）；举报/申诉证据（ReportEvidence/AppealEvidence）以 JSON 数组内嵌主表，放弃结构化查询能力换取表数量收敛——若运营需按证据检索再拆表（变更流程）。
