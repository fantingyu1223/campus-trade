## 1. 为什么三方法论结合

三种方法论在本体系中各司其职，互不替代，按"语义 → 思想 → 工程"三层叠加：

| 方法论 | 角色 | 在本体系中的落点 | 对应目录 |
|---|---|---|---|
| **本体论（Ontology）** | 语义地基 = 统一语言（Ubiquitous Language 的严格化） | 对领域内每个名词给出严格定义、属性边界、约束与同义词辨析，消除"交易/订单""取消/拒收"等歧义，是 PRD 与自然语言讨论到形式化模型的第一道过滤器 | `ontology/` |
| **DDD（领域驱动设计）** | PIM 的落地思想 | 提供限界上下文（Bounded Context）、聚合（Aggregate）、领域事件（Domain Event）等结构化手段，把本体概念组织成可演进的系统结构；与技术方案的模块划分（§3.1）对齐但**不绑定实现** | `pim/` |
| **MDA（模型驱动架构）** | 工程方法 | 提供 CIM→PIM→PSM→代码 的转换框架与双向追溯（traceability）纪律，保证"需求变了改哪些模型、模型变了改哪些表/接口"可机械回答 | `cim/` `pim/` `psm/` `traceability.md` |

**结合方式一句话**：本体论保证"我们说的是同一个东西"；DDD 保证"系统结构按业务边界切分"；MDA 保证"从业务到代码的每一步映射留痕、可回溯"。

**层级对应关系**：

```
PRD（冻结，自然语言）
   │  语义抽取：名词严格定义、歧义消除
   ▼
ontology/ 领域本体（ONT-xx）────────────── 语义地基，贯穿三层
   │  业务视角建模（不涉及系统）
   ▼
cim/ 计算无关模型（CIM-E/P/R-xx）          业务实体/流程/规则
   │  CIM→PIM 转换：业务到系统的映射决策留痕
   ▼
pim/ 平台无关模型（PIM-BC/AG/EV/SM-xx）    限界上下文/聚合/事件/状态机
   │  PIM→PSM 转换：按目标平台规则映射（小程序TS + NestJS/Prisma + MySQL8 + Vue3）
   ▼
psm/ 平台相关模型（PSM-xx）                表/接口/模块结构一一对应
   │  PSM→代码：与 server/ miniprogram/ admin-web/ 实现对齐
   ▼
代码与契约（server/src/contract 等）
```

## 3. 编号规范（全体系沿用，不得变更）

| 前缀 | 含义 | 示例 |
|---|---|---|
| `ONT-xx` | 本体概念（语义层） | ONT-01 商品 |
| `CIM-E-xx` | CIM 业务实体 | CIM-E-01 闲置商品 |
| `CIM-P-xx` | CIM 业务流程 | CIM-P-01 双模式交易流程 |
| `CIM-R-xx` | CIM 业务规则 | CIM-R-01 取消 24h 默认同意 |
| `PIM-BC-xx` | PIM 限界上下文 | PIM-BC-01 交易上下文 |
| `PIM-AG-xx` | PIM 聚合 | PIM-AG-01 订单聚合 |
| `PIM-EV-xx` | PIM 领域事件 | PIM-EV-01 订单已支付 |
| `PIM-SM-xx` | PIM 状态机 | PIM-SM-01 订单五态状态机 |
| `PSM-xx` | PSM 平台相关模型元素（表/接口/模块） | PSM-01 trade_order 表 |
| `F1-F39` | PRD 功能编号 | 直接引用，不另编号 |
| `N1-N9` | PRD 非功能编号 | 直接引用 |
| `O1-O10` | PRD Out of Scope 编号 | 直接引用 |

规则：
1. 编号一经分配**不复用、不改号**；元素废弃时标注 `已废弃` 并保留编号与废弃原因。
2. 同层内编号连续递增；跨层引用必须写全编号（如 `ONT-07`），禁止只写概念名。
3. PRD 功能号（F/N/O）是追溯的锚点，每个模型元素须标注其来源功能号。

## 4. 追溯规则

1. **每个模型元素必须有**：稳定编号 + 来源引用（PRD 功能号/条款 或 上层模型编号）+ 去向引用（下层模型编号 或 实现位置）。
2. **双向追溯**：向上能回答"这个模型元素从哪条需求来"；向下能回答"这条需求落到哪些模型/表/接口"。
3. **追溯矩阵**（`traceability.md`）是唯一追溯事实源：新增/变更任何模型元素，必须在同一提交内更新追溯矩阵，否则视为变更未完成。
4. 发现 PRD / 契约 / 实现三者不一致时，**mda-engineer 只上报冲突清单，不自行裁决**（角色边界）。

## 5. 模型变更流程（与 PRD/契约冻结规则一致）

对齐 PRD §1.2 冻结规则与技术方案 §5 契约变更规则：

1. **提出**：任何层模型变更须注明触发源（PRD 变更 / 契约变更 / 实现对齐 / 建模勘误）。
2. **裁决**：涉及口径变化（规则数值、状态枚举、权限边界）的变更，须 **CEO 裁决 + 会议纪要**；纯表述勘误（不改变语义）可由 mda-engineer 直接修订并记录。
3. **升版本**：变更生效后相关模型文件升版本号（v1.0→v1.1…），文件头修订记录留痕。
4. **同步波及面**：按追溯矩阵找出受影响的上下游模型层，全部同步更新，并在变更说明中列出影响面清单；追溯矩阵同提交更新。
5. **状态标记**：未经 CEO 审核的模型一律标 `状态：待 CEO 审核`。

## 6. 图法约定

- 图一律用 **Mermaid** 文本嵌入 Markdown（`classDiagram` / `stateDiagram-v2` / `sequenceDiagram` / `flowchart`），保证可版本管理、可 diff。
- 状态机图的状态命名必须与 PRD 枚举逐字一致（如订单五态：待交货/待确认/已完成/已取消/申诉中）。
- 实体/属性命名在 PSM 层与 `server/prisma/schema.prisma` 及 `server/src/contract/` 保持一致。
